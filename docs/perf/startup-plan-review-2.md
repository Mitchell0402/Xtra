## 2. 新问题

### N1（必须改）配置文件装上了没有，要直接验证

计划的准备流程是：首启 → 等 5 秒 → `force-stop` → 广播 → 编译 → 检查 dexopt 状态是 `speed-profile`。有三个漏洞：

- **dexopt 状态证明不了是 APK 的配置文件。** 首启那 5 秒里 ART 的 JIT 也会记一份配置文件，编译时会合并进去。就算广播失败，`speed-profile` 也可能照样出现，只是里面只有首启 JIT 记到的那一点方法。
- **广播放在 `force-stop` 之后有风险。** `force-stop` 会把包重新置成「已停止」，系统默认不把广播投给已停止的包。U8 那次成功的广播是不是在停止之后发的，日志里看不出来。
- **结果码只说了「记下」**，没说哪个算成功。

要改的：

1. 广播放在 `force-stop` **之前**（首启后进程还活着时发），或者给 `am broadcast` 加 `--include-stopped-packages`。
2. 结果码只接受 `1`（`RESULT_INSTALL_SUCCESS`），别的值整组作废并在日志里写出原因。
3. 编译后加一步直接看配置文件内容：`cmd package dump-profiles --dump-classes-and-methods <pkg>`，读 `/data/misc/profman/<pkg>-primary.prof.txt` 数类和方法的行数（Macrobenchmark 在 API 33 以上取配置文件就是这么做的）。U9 应该是几千到上万条（APK 里有 4,065 个类、约 1.29 万个启动方法），v0.1 是几百条（3 KB 的库规则加首启 JIT）。数量级不对就作废。第一种方法（参考组）的同一个数字也记下来，正好说明两种方法的差别。

### N2（必须改）「温启动：返回键退出后再开」测的是热启动

Android 12 起，在任务的根 Activity 上按返回键，系统默认把任务移到后台，不结束 Activity。`MainActivity` 没有自己处理根上的返回（只在画中画的音频按钮里 `moveTaskToBack`，第 359 行），Compose 的 NavHost 在只剩起始页时也不拦返回。所以按计划的做法，「温启动」和「热启动」测的是同一件事，都不经过 `onCreate`。

这条要紧，因为 S2、S3 挪动的东西全在 `onCreate` 和首帧里，真正可能被它们拖慢的是温启动（Activity 重建、进程还在）。

要改的：

1. 每次 `am start -W` 都解析输出里的 `LaunchState:`，和这次想测的模式（COLD / WARM / HOT）不一致就作废。冷启动也一样检查，能顺便抓住「`force-stop` 没生效」。
2. 温启动换一种能真正结束 Activity 的做法，例如会话里临时打开「不保留活动」（`settings put global always_finish_activities 1`，跑完还原，和旋转设置一起写进还原清单），再按 Home、重新打开。做不到就在第 1.2 节写明只测热启动，并说明温启动没有覆盖。

### N3（必须改）首帧后 1 秒主线程忙碌时间的限值和计划的做法冲突

第 1.2 节要求「第一帧之后 1 秒内主线程忙碌时间不多于 U9 的 105 %」。但 D1（吐司层首帧后在主线程空闲时 `setContent`）本来就是把主线程工作从首帧前挪到这一秒里；B1、B3、D5 的后台工作也会和主线程抢核。这个限值越做越容易超，超了也不说明变差了。

要改的：限值改成看**总量**，即「从进程启动到第一帧后 1 秒」主线程 Running 时间不多于 U9（允许 3 % 的噪声）；「第一帧之后 1 秒」单独那段只报告、不设限，用来看工作被挪到了哪里。这样既能证明工作是「挪了」不是「多了」，也和「前 10 帧」那条一起盯住首屏刚出来时的卡顿。

### N4 测量包名再细一点

- **每个被测的版本一个包名。** 计划里 U9 和新版共用 `.qa.perf`，要轮流全新安装；P0 的「不压缩 dex」对照包也只能用同一个包名；第 1.2 节温启动、热启动要「和 U9 同会话比」，也得来回装。建议 `-Plagoon.perfId=<名字>` 生成 `.qa.perf.<名字>`（如 `.qa.perf.u9`、`.qa.perf.new`、`.qa.perf.nocompress`），几个包能同时装、直接交替。
- **U9 对照包不用从 tag 拷源码打。** `ui-u9` 那份代码里没有 `-Plagoon.perfId`，照计划做还得手工打补丁。既然 tag 之后 app 代码没变，S0 加完构建属性后，从那个提交打 `.qa.perf.u9` 就是 U9，记下提交号即可。
- **核对重打的包只改了包名。** 重打的 v0.1、U9 qa 包，`classes.dex` 和 `baseline.prof` 的大小应该和 `Lagoon-baseline` 里的原包几乎一样（v0.1 qa 8,517,812 / 3,006 字节，U9 qa 9,287,580 / 9,101 字节），差得多就说明工具链或源码不一样，先查清再测。
- **卸载白名单的写法。** 用精确的包名集合（或首尾锚定的正则），不用前缀或后缀匹配，否则 `io.github.mitchell0402.lagoon`（正式版）和 `.qa` 都可能被误匹配。脚本每次会话开头和结尾把 `pm list packages | grep mitchell0402` 写进日志，开头发现 `.qa` 或正式版就照常跑、绝不碰，结尾核对它们还在。脚本不带 `-s` 序列号直接退出（模拟器和手机可能同时连着）。
- 白名单里有 `.bench`。只要决定 3 选了「登录录制」，这个包上的登录就会被下一次准备流程卸掉；Gradle 跑 `:benchmark` 的 connected 测试默认也会在跑完后卸载目标包。这是决定 3 建议不登录的原因之一。

### N5 吐司层：启动时的吐司本来就不走吐司层

`LagoonToasts.show()`（`GlobalToasts.kt` 第 47–53 行）在 Activity 还没到 STARTED 时直接用系统吐司。`onCreate` 第 189 行那条断网吐司发生在 STARTED 之前，所以**现在就是系统吐司**，和吐司层什么时候建立无关。之后的吐司走 `ToastHostState`，它自己有互斥锁排队，吐司层只是读 `current` 来画，晚点建立也不会丢。

所以 D1 里「启动吐司排队」不需要新代码，修改版 2 可以删掉这句，只保留装饰初始值和无障碍两条。剩下的小影响：如果在 STARTED 之后、吐司层建立之前就有吐司，它的计时从 `show()` 开始，显示时间会短几十到几百毫秒，可以接受。

附带发现（不属于本计划）：断网冷启动时用户看到的是系统样式的吐司，不是 Lagoon 的玻璃吐司。这是 U9 留下的不一致，要不要改由 Mitchell 定，建议单独记一条。

### N6 唤醒和锁屏检查要「查不到就作废」

`dumpsys power` 里的 `mWakefulness` 和 `dumpsys window` 里表示锁屏的字段名在各 Android 版本、各厂商系统上不一样。脚本找不到字段时应当作「不满足」作废并报错，不能当作通过。第一次在 Android 17 的 OnePlus 上跑之前，先手工核对一次字段名写进脚本注释。

### N7 bootstrap 区间写清楚

建议写成：按「对」（同一轮里的一次 v0.1 和一次新版）有放回重抽 30 对，算两边中位数之比，重复 10,000 次取 2.5 % 和 97.5 % 分位。区间跨过 1.10 时写「勉强过」，计划这条规定可以保留。

### N8 小处

- 第 1.2 节的「前 10 帧」用 bench 包的 trace 测，要扣掉 P0 量到的 bench 和 qa 的差，或者只和 U9 bench 比（建议后者，写明）。
- S0 第 1 步的脚本在用手机之前，先在模拟器空闲时空跑一遍（准备流程、`LaunchState` 解析、白名单、N1 的配置文件计数），把错误在不占手机时间的地方找出来。
- 登录冒烟（第 1.2 节）写明装哪个包、谁登录、做完之后这个包会不会被下一次会话卸掉。

## 3. 第 10 节五个决定的建议

1. **P0 什么时候开始：先把 S0 第 1 步做完、在模拟器上空跑通过，再约一次约 1 小时的手机时间。** 不要在脚本落地之前占手机。脚本、包名属性、几个测量包这一步不需要手机，可以批准后马上做；做完由我在线程里请 Mitchell 定具体时间。
2. **P0 后如果 U9 已经 ≤ 1.10：同意缩小成「保住并加固」。** 具体做 S1（便宜、不改行为），加 S2 里把握「中」以上、风险低的三项：B1 WorkManager、B3 字体、C1 网络查询，然后走 P2、P3。P0 只是一次会话，过线还是要靠 P2、P3 两次都过。
3. **配置文件录制：只录未登录。** 门槛场景本身就是全新安装、未登录；登录状态多出来的工作（列表、图片）都在第一帧之后，不进 TTID；而 `.bench` 包每次准备和每次 Gradle 跑测试都会被卸载，登录会反复丢，每次都要 Mitchell 亲手再登。登录冒烟里如果看到明显变慢，再回来考虑。
4. **S4 之后仍 > 1.10：接受现状，不授权改首帧结构。** 前提是账本说明剩下的差距主要是 Compose 运行时本身，并且第 1.2 节各项都过。S4 里每项要先在 trace 里看到对应的大块开销才做，会改视觉或交互的一律先问。
5. **Conscrypt：同意不进本计划，建议单独开小 PR 删掉。** 收益比计划写的还大：U9 qa 包 15.9 MB 里 `libconscrypt_jni.so` 四个 ABI 合计约 10.4 MB（不压缩存放），删掉后包大约只剩三分之一多一点。代码里只有 `XtraApp` 里 `< Q` 那段用它（最低 API 29，不会执行）。OkHttp 5 在 Android 上用系统的 TLS（`Android10Platform`），它的 `ConscryptSocketAdapter` 只处理应用自带 Conscrypt 建的连接，没有这个库就不启用。验证：API 29 模拟器和手机上 OkHttp、Cronet、HttpEngine 三种网络库各打开关注页和一个直播，看请求正常、走 HTTP/2。这和启动无关，可以和本计划并行。
